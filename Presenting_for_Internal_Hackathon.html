🤖 4. AI & Machine Learning Suite Details

GramVistaar uses a 3-tier hybrid AI architecture combining Generative LLMs, Local Speech Recognition, and Named Entity Recognition (NER).

1. Groq LLM Feasibility Engine (llama-3.3-70b)

- Purpose: Generates hyper-local business SWOT, demand narratives, and pricing guidance.
- Guardrails: Strictly constrained system prompts prevent numeric hallucination. All financial numbers are pre-calculated by JS before passing into LLM context.
- Provenance Tagging: Enforces 4-tier metadata tagging on every generated insight.

2. Multilingual Voice ASR & NER Pipeline

- Speech-to-Text (ASR): Quantized Whisper-tiny / Bhashini API Roadmap transcribes voice inputs in regional dialects (Bhojpuri, Maithili, Hindi).
- Named Entity Recognition (NER): Custom SpaCy / BERT-tiny NER model extracts slot values: {B-VILLAGE, B-CAPITAL, B-CATEGORY}.
- Result: Zero-typing form auto-fill for illiterate or semi-literate rural micro-entrepreneurs.

Pitch Speech Line to Recite:

A rural user can simply speak: 'Hum retail dukaan kholna chahte hain, ₹10,000 margin hai' — and our NER engine extracts village location, capital, and trade category into the financial calculation loop!"

❓ 8. Exhaustive Judge Q&A Bank (All Sections & Hidden Traps)

This bank contains standard technical questions, new database/dashboard questions, Bhashini clarification, and hidden trap questions.

Category A: Problem Statement & Vision

Q1 Why build GramVistaar as a guided web platform instead of a WhatsApp Chatbot or generic LLM Chatbot?
Answer: Rural micro-entrepreneurs evaluating a ₹1,00,000 to ₹10,00,000 government loan need structured decision-making, clear numbers, side-by-side financial comparisons, and shareable PDF documents for bank managers. Conversational chatbots suffer from three critical flaws:
  • Hallucination Risk: Open-ended chatbots invent loan terms or miscalculate EMIs.
  • Cognitive Load: Unstructured text walls confuse beneficiaries who need visual financial tables.
  • Lack of Provenance: Chatbots cannot visually tag which line item comes from Census 2011 vs which comes from an economic estimate.

Category B: Database, User Dashboard & Reminders

Q2 What database architecture are you using for village lookup and user data?
Answer: We use a 2-tier database strategy:
  • Tier 1 (Village Lookup): Pre-computed static JSON datasets (data/village_metrics.json) covering 202 census villages for zero-latency (<10ms) public feasibility lookups.
  • Tier 2 (User & Loan Tracking): A PostgreSQL database (via Supabase) with Row Level Security (RLS) for storing beneficiary user profiles, uploaded KYC documents, and loan repayment schedules.
TRAP Q3 How will users track their loan status and avoid missing EMI repayments?
Answer: Our product roadmap includes a Beneficiary Loan Tracking Dashboard where users log in via Aadhaar OTP:
  • Application Tracking: Real-time status update from State Channelising Agencies (SCAs).
  • Document Locker: Secure upload of Aadhaar, Caste, Domicile, and Income certificates.
  • Automated Reminders: Integration with WhatsApp Business API and Government SMS Gateway (NIC) to send automated payment reminders 7 days before EMI due dates.

Category C: Language Localization & Bhashini API Clarification

TRAP Q4 Is Bhashini API live in your current build, and how does your Hindi translation work?
Answer: Here is our exact, bulletproof answer:
  • Current Live Prototype: We generate Hindi (Devanagari) feasibility reports using Groq LLM (`llama-3.3-70b`) with strictly constrained bilingual system prompts, paired with a sub-second client-side translation dictionary in `public/app.js` for UI labels. This guarantees zero-latency, sub-second responses without relying on external sandbox keys during live hackathon testing.
  • Production Government Deployment: Our translation architecture is designed to plug directly into MeitY's official Bhashini REST API (via ULCA API keys) to scale voice & text support across all 22 Scheduled Indian Languages (including regional dialects like Bhojpuri and Maithili).

  • Zero Code Rewrite for New States: Scaling to all 600,000+ villages only requires ingesting official Census CSV datasets into our JSON schema.

Category E: Data Authenticity, Census 2011 & Financial Math

Q6 Where does your village data come from, and how do you ensure its authenticity?
Answer: Our dataset covers 202 census villages across two districts in Bihar (Muzaffarpur & Gaya). Sourced directly from:
  • Census 2011 Village Directory (data.gov.in) for primary village demographics and worker numbers.
  • SHRUG (DevDataLab) (devdatalab.org/shrug) for economic amenities.
All population numbers carry a green [Verified: Census 2011] provenance badge.
TRAP Q7 What are the official loan caps, interest rates, and moratorium rules in your platform?
Answer: Official NSFDC/NBCFDC guidelines implemented in src/modules/financialCalc.js:
  • Term Loan Scheme: Project cost > ₹1.40L up to ₹10.0L $\rightarrow$ 8.0% p.a. interest, 6-month moratorium, 7-year tenure.
  • Micro Finance Scheme: Project cost ≤ ₹1.40L $\rightarrow$ 6.5% p.a. interest, 3-month moratorium.
  • Loan Ratio: 90% Scheme Contribution, 10% Borrower Margin Capital.
  • Income Ceiling: Official MoSJE unified ceiling of ₹3,00,000 / year.

Category F: AI / LLM & Hallucination Defenses

TRAP Q8 LLMs hallucinate. How do you prevent LLMs from giving wrong financial advice?
Answer: Architectural Decoupling:
  • Zero Math in LLM: The LLM is NEVER allowed to compute loan amounts, interest rates, or EMIs. All numbers are computed deterministically by our JS engine.
  • Strict System Prompt: The Groq API system prompt explicitly forbids inventing new numbers.
  • 4-Tier Provenance Enforcement: Every section of the narrative must tag its source ([Verified], [Derived], or [AI-Estimated]).
