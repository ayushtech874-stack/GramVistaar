Part 1

Why does this need to exist?

Read the problem statement's own closing clause again: an EMI/moratorium schedule generated before the person applies. That "before" is the whole justification.

Concessional schemes like NSFDC's are genuinely generous — 90% financed at low interest, once someone contributes their 10% margin. The failures happen after disbursement, not because the money wasn't available, but because of two decisions made badly at the very start:

  • The business was picked on instinct, not on whether the specific village/block could actually support it.
  • The applicant didn't understand their own numbers — exact eligible loan amount, correct scheme tier, real repayment burden once the moratorium ends.

Both are decision failures, not funding failures. The need is narrow and real: catch bad decisions once, at the start, with better information — not build a broader fintech or lending platform.

Part 2

What does 1 block per district actually prove?

"If I get datasets for 1 block each in 2 districts, what change will it actually work?"

It doesn't help the whole country — and it isn't supposed to. It proves three narrower, checkable things to a jury:

  1. The mechanism works. A real village, real numbers, a real result on screen — not a mockup.
  2. The pipeline generalizes. If Muzaffarpur and Gaya both run on the same code with just different data files, adding a third district later is a data-import task, not a rewrite. That's the scalability argument, demonstrated instead of asserted.
  3. You can defend your numbers. "How do you know that" gets answered with an actual Census citation for an actual village, not a gesture at "our AI analyzes local data."

Think of it as a working scale model, not a toy — a judge isn't expecting rural credit access solved nationally in 36 hours; they're checking whether what exists is real and whether it plausibly scales if funded further.

Part 3

Who is this for?

Primary: a first-time rural/semi-urban applicant — has savings, is eligible for a concessional scheme, doesn't know which scheme applies or whether their business idea is sound.

Worth designing for honestly: many people in this exact situation go through a facilitator — a Common Service Centre operator, an NGO worker, a Haqdarshak-style local agent — who runs the tool for them. A guided, form-based flow naturally supports both self-service and facilitator-operated use. Don't assume the end beneficiary always types it in themselves.

Part 5

How AI + database actually work — and why it's not a chatbot

The database is not "live" in any sense — it's a small table built once, offline, before the app runs: one row per village, with the real population/establishment numbers already being collected (see datacollection.html). At runtime the app does a plain lookup — "give me the row for Saghari Rampur" — the same way a spreadsheet VLOOKUP works. No live scraping, no external calls mid-demo.

The AI's job is narrow and one-shot, not conversational

  1. User fills a form (village, capital, category, eligibility fields) — not a chat message.
  2. Backend looks up real numbers for that village and runs the deterministic math.
  3. Those real numbers get inserted into one fixed prompt template and sent to the LLM once.
  4. The response renders as a report on a results screen — not chat bubbles the user replies to.

No back-and-forth, no conversation memory, no "ask me anything." The AI is a report-writing engine invoked behind the scenes — like mail-merge, just smart enough to write good sentences instead of filling blanks. A chatbot is a conversation interface; this is a form-in, report-out tool where AI is one internal step, invisible to the user as "chat."

Part 8

On what basis does the LLM write the SWOT / feasibility report?

"On what basis is the LLM going to decide the SWOT analysis and what all things are required?"

The LLM is combining two different kinds of input, and it's important to be precise about which is which:

  • Real local numbers, given to it directly — population, establishment counts per category, consumption estimate, all pulled from the pre-built village table. These are facts, not something the LLM is asked to figure out.
  • General business-domain reasoning already in the model from training — how a dairy business's SWOT typically looks, what threats a small retail unit typically faces, general pricing logic. This is pattern knowledge the LLM already has, applied on top of the real numbers.

The instruction to the LLM is explicit about the boundary between these two: use the real numbers as ground truth, apply general business reasoning around them, and never invent a specific local number that wasn't given. This is why every sentence in the output gets tagged — Verified (from the table), Derived (calculated from the table), or AI-Estimated (the LLM's own reasoning layered on top) — so the two kinds of input stay visibly distinguishable in the final report rather than blurring into one undifferentiated block of text.

Concretely, the LLM is told: "Here is real population X, real establishment count Y for this category, real consumption estimate Z. Using only these as fact, write a SWOT, opportunity gaps, threats, and pricing guidance for this business category at this location. Tag every sentence by source. Do not state any specific number not given to you above."

Part 9

The exact financial calculation

"What type of calculation do I need to do?"

calculation-logic.txt
project_cost = available_capital / 0.10
loan_eligibility = project_cost * 0.90

if project_cost <= 140000:
    scheme = "Micro Finance Scheme"; rate = 6.5%; tenure = 3 yrs; moratorium = 3 mo
    loan_eligibility = min(loan_eligibility, 125000)
elif project_cost <= 5000000:
    scheme = "Term Loan Scheme"; rate = 8%; tenure = 7 yrs; moratorium = 6 mo
    loan_eligibility = min(loan_eligibility, 4500000)
else:
    # outside any tier - show nearest tier and what would need to change,
    # never silently default

emi_schedule = standard reducing-balance EMI, moratorium period excluded
              from principal repayment (confirm interest-only vs capitalized
              treatment from the scheme document before hardcoding)

Zero AI involvement here — pure arithmetic against the hardcoded scheme terms from Section 6. This is the piece that must be exactly correct, since it's the credibility anchor of the whole pitch (unit-test it against the PS's own worked example plus a few hand-computed cases).

Part 13

Should the platform pick the business for them?

"They picked a business on gut feeling, not on their village's market — so should our platform decide for them which business is suitable?"

Decided: no full recommendation engine — but the gut-feeling problem is still addressed

Why not a full recommendation engine

  • The PS's own input schema requires business category as an input, not an output — a full recommendation engine flips that core assumption and roughly doubles your AI/prompt-design surface area (you'd need to score and rank every possible category, not just narrate one).
  • This was already logged as deferred Future Scope, not rejected outright — strong evidence exists that this is a real market gap (see the earlier competitor research), so it's a good post-hackathon direction.

What actually solves the "gut feeling" problem without needing that build

The feasibility report itself already does this. If a user picks Dairy and the report shows a saturated local market and a weak SWOT, that's already steering them away from a bad decision — without the platform needing to prescribe what to pick instead. The failure mode named in the PS ("picked on anecdote, not data") is fixed by showing them real data about their chosen category, not by replacing their choice.

Optional middle-ground stretch feature, if time allows: let the user run the feasibility check for 2–3 categories side by side, so they can compare fit themselves. This is user-initiated comparison, not an automatic ranking/recommendation — it stays inside the PS's own input-driven design while still addressing the underlying "gut feeling" concern. Build this only after the single-category core loop works end-to-end.

Part 14

Implementing in Antigravity — database, data-feeding, and the RAG question

"How am I going to implement this using Antigravity — the database, the data I've already collected, where do I feed it, should I use RAG, how does the LLM fetch and work on it?"

Short answer on RAG

No — not real RAG. RAG (vector embeddings + semantic search) is for retrieving relevant text out of a large, messy, unstructured document pile. What you have is a small, structured table with a clear lookup key (village name/ID) — that's a database lookup problem, not a search problem. A plain WHERE village_id = X query finds the right row instantly and with zero risk of retrieving the wrong thing, which vector search can occasionally do. Building a vector database here would be solving a problem you don't have.

What actually happens, step by step

  1. Format the already-collected data. Take the real Aurai/Sherghati figures from datacollection.html Section 13 and turn them into the flat village_metrics table shape defined in schema.md — a CSV or JSON file, one row per village.
  2. Load it once, at backend startup — into Postgres, or just read from the JSON/CSV file directly (decisions.md D10 — flexible, pick whichever your Data/Database owner is fastest with).
  3. On each user request, the backend does a plain lookup by village_id, gets back real numbers (or nulls for missing fields).
  4. Those numbers get inserted into the fixed prompt template from Section 8 and sent to the LLM API once per request.
  5. The response is parsed, each sentence checked for a tag, and rendered on the results screen.

What to tell Antigravity explicitly

Feed it the existing context pack (PRD.md, tech-spec.md, schema.md, rules.md, app-flow.md) as project files, plus this document and datacollection.html. Then be explicit in your first prompt to the agent:

first-prompt-to-antigravity.txt
Build the backend exactly per tech-spec.md and schema.md.
Local data retrieval is a direct table/JSON lookup by village_id -
do NOT implement vector search, embeddings, or a RAG pipeline for this.
The LLM is called once per request, only after the deterministic
eligibility, financial, and local-metrics modules have already run.
Enforce rules.md R2 (no-invention rule) at the code level: any null field
in village_metrics must return "Insufficient Data" explicitly, never a
generated substitute.

What to actually take care of during the build

  • Keep the DB schema matching schema.md exactly — if a field changes, update schema.md first, then code.
  • Null-check before every LLM call — the module that does the lookup must decide "insufficient" status itself, before the prompt is even built.
  • Validate LLM output tags after the fact — don't trust the model to tag every sentence correctly; default any untagged sentence to AI-Estimated, never Verified.
  • Keep the financial/eligibility modules untouched by any AI call — those stay pure functions end to end.
